# ftscr submission plan

Written before importing the implementation into this repository on 14 October
2026. This is a submission preparation plan: a previously developed API-only CLI
and its tests are the starting point, not newly written code attributed to this
plan. The previous repository remains a separate reference.

**Goal:** Deliver a self-contained public `ftscr` repository that an evaluator can
clone, run, inspect and use to generate Paris 2024 football reference JSON.

**Architecture:** Retain the tested flow: official API → saved snapshot → parse →
validate → select → sort → JSON. Network access belongs only to `fetch`; ordinary
generation and tests use the committed snapshot. Use simple functions and types.

**Stack:** TypeScript, Node.js 24, npm, ESLint, Node's built-in test runner and
GitHub Actions. No production dependencies.

**Specification:** Original assignment and example will be preserved as
`docs/assignment.md` and `example.json`. The agreed interpretation is JSON response
bodies, API-only source data and three selectors: all matches, one country, or a
country pair. Unknown facts stay `null`; added time is represented as `"90+3"`.

## Constraints and file responsibilities

- Keep the previous repository unchanged; create independent Git history.
- `src/`: preserve the existing CLI, source, parsing, validation, filtering,
  serialization and type boundaries. Improve formatting, not business rules.
- `tests/`: retain the existing regression tests and independent golden response.
- `fixtures/`: preserve the official snapshot and original retrieval manifest.
- `README.md`: evaluator-facing installation, usage, distribution, assumptions
  and discussion points. Keep only technical submission documentation.
- `AGENTS.md`: portable instructions for plan → implementation → validation.
- `docs/plan.md`: this plan. `docs/verification.md`: actual verification evidence.
- `.github/workflows/ci.yml`: reproducible checks and downloadable JSON artifact.
- Do not copy the old Git history, local captures, generated files or dependencies.

## Review focus

1. Clean checkout: installation and all documented commands must work without the
   old repository, local tools, private links or uncommitted files.
2. Data fidelity: snapshot provenance and the two unavailable goal minutes must
   remain visible; formatting must not change generated bytes.
3. Selection: country aliases, reversed pairs and repeated pairs retain their
   existing behavior, with ambiguity reported rather than resolved arbitrarily.
4. Publication: package name, CLI help, documentation and CI must describe `ftscr`;
   tracked contents must be appropriate for a public submission.
5. Evidence: distinguish the original snapshot retrieval from new validation;
   report only observed local checks, independent review and hosted CI results.

## Scope decisions

The tested parser is reused rather than rewritten to create artificial development
history. New automated tests are needed only for substantive behavior changes or
review findings; formatting and documentation use regression and smoke checks.
This short, portable plan and `AGENTS.md` are sufficient for the workflow; running
the application does not require any particular AI tool or agent skill package.
